## IOP Interface Design
Considered the necessity of an input data register.
* The purpose of an IPDR is to ensure the signal remains synchronized with the internal clock cycle
* Despite this, if the input signal is wired directly to the write back mux, the signal should remain intact virtually all the time. 
* Assuming the inputs are push buttons and switches, bypassing an IPDR should work.
* If a more complex signal were connected to the input peripheral, such as a UART signal, an IPDR would be necessary.

## Initial visual verification
In visualizing how the different instructions would be executed in the data path, some issues in the first iteration became apparent:
* MAX needs to differentiate between rsA and PC for branch, jump & load, jumpR
	- Resolved by adding a select MUX controlled by the control unit
* Branch conditions need to be implemented without CNVZ registers (CNVZ not naturally stored in RISC-V architecture)
	- Considered the tradeoffs of using the ALU subtract function vs creating dedicated subtract compare hardware for branch conditions
		* Using preexisting ALU reduces hardware, but may require an additional machine cycle
		* Creating dedicated hardware would prevent the need of an additional machine cycle, but would greatly increase hardware cost, and may impact critical path delay
	- Ultimately concluded reusing the preexisting ALU would be the optimal decision
	- Resolved by adding a 2-bit NZ Res output from the ALU to be compared by the CU
* It is noted the PM/DM combined memory array may not be possible using Quartus design tools
	- If it is not, standard Harvard architecture will be utilized
	- **NOTE: It has been determined Quartus DOES support combined memory arrays**
	
## Commencement of ASM chart design
It is expected that as the ASM chart is designed, further datapath issues will be detected and resolved.
* Load complications:
	- Current datapath does not account for LB, LH, LBU, or LHU. Will need to add an additional multiplexer to account for partial words. 
	- Not an issue for store as Quartus has the ability to include this functionality in the memory block
* Type U complications:
	- Hardware not currently configured to handle LUI, and AUIPC needs MARout connected to the WBmux to work.
	- LUI can likely be solved by bitmasking off the rd and opCode from the IW and directed to the WBmux.
