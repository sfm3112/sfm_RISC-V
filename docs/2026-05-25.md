## Core Instruction Word Research
Spent time evaluating 16-bit (Compressed / RVC) vs. standard 32-bit RISC-V instruction word formats. 
* **Observations:** Noticed key alignment vectors in the 2 LSBs of the opcodes and bits 4:3 of the immediates. The sign bit for the 16-bit variant consistently lands on the 12th bit.
* **Design Decision:** To maintain pipeline simplicity and optimize FPGA resource usage for this iteration, I am bypassing the compressed extension and sticking strictly to a uniform 32-bit instruction word length. May return to compressed instructions if time permits.

## Architectural Choice: Hybrid Harvard-Von Neumann Memory
Originally considered a strict Harvard architecture (completely separate program and data memory blocks). However, to streamline the physical memory footprint on the target FPGA, I am adopting a **Hybrid Harvard-Von Neumann architecture** theoretically possible via a dual-ported SRAM array.
* **The Benefit:** Both program code and application data will reside in a single, unified memory space (Von Neumann style), but the dual-ported design allows the instruction fetch stage and the data load/store stage to access the array simultaneously in a single clock cycle (Harvard style), eliminating structural memory hazards.

## Datapath Iteration 1.0
Drafted the initial structural block diagram for the CPU core datapath:
* **Register File:** Implemented a 32-word general-purpose register file (`r0` through `r31`). Note: `r0` will be hardwired to `32'b0` in the SystemVerilog source.
* **ALU Optimization:** Successfully mapped the ALU source multiplexer select line directly to `IW[5]`. This leverages the RISC-V opcode structure to differentiate Register-Reg vs. Register-Imm instructions without requiring secondary decoding logic.
* **Address Generation:** Integrated a dedicated address calculation adder ($MAX + MAB$) to decouple load/store address calculations from the main ALU, optimizing critical path timing.
