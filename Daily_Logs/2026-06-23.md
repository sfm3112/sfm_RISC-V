## Debugging Observations & Analysis
When running the dynamic testbench with the first assembly instruction (`addi x1, x0, 2`), the execution failed with an unexpected register result. Detailed trace analysis reveals a major communication mismatch between the Datapath (DP) and the Control Unit (CU):

* **Datapath State:** The Datapath is pulling and capturing the instruction successfully. The testbench reports `Instruction Word: 0x200093` and an `ALU result: 2`. The lower 7 bits of this instruction correctly decode to `7'b0010011` (`TYPE_I`), meaning the datapath hardware itself is evaluating the instruction properly.
* **Control Unit State:** The Control Unit's tracker logs `CU State Changed: MC1 Processing Unknown Opcode (0x00)`. Because it reads `0x00` instead of `0x200093`, its internal `always_comb` block misses the `TYPE_I` case entirely and hits the `default` fallback.
* **Resulting Chain Reaction:** In the fallback state, the CU sets `WBsel = NA` (value `7`) and forces the register write-back enable signal (`LDrd`) to `0`. Consequently, no data is written to the destination register, resulting in `ACTUAL RESULT: x1 = 0x0` instead of the expected `0x2`.

## Hypothesis & Bug Root Cause
There is a fundamental top-level structural wiring issue. While the Datapath instruction register (`IWRreg.Q`) is loading the correct instruction, that data bus is not reaching the Control Unit's input pin. The `IW` input port on the `sfm_riscv_CU_sv` module is likely left completely floating, tied to ground, or mapped to an incorrect wire in the top-level wrapper module.

### Reset Phase Analysis & Gated Clock Glitch Discovery
Upon closer observation of the simulation timeline at 10.00 ns, a separate breakdown occurs immediately following the reset phase:

* **The Symptom:** The Python testbench drives `rst` high for 2 clock cycles and drops it to `0` at exactly 10.00 ns. At this precise timestamp, the Control Unit transitions to state `MC0`. 
* **The Error:** Simultaneously at 10.00 ns, the instruction register (`IWRreg`) captures `32'bX` (completely uninitialized/unknown data) on its output bus `IW` instead of latching the first valid instruction word. Because `IW` becomes `X`, the simulator throws a setup/hold or unparseable value violation, locking the state machine into an infinite `default` loop that prevents the core from executing any instructions.
